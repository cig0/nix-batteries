# Public backports and release checks

The private repository remains the development source. The public derivative
receives selected patches; its sanitized history is never merged with private
history. Public author identity, host names, consumer aliases, and library APIs
remain intentional. The option-catalogue implementation and fixture are retained
for direct import; their public export and check registration remain a separate
migration phase. Review reports, assessments, and private audit artifacts are
excluded from the public release tree.

## Transferring a change

From the private repository, write the selected commit range to a patch outside
the public tree with `git format-patch --stdout <base>..<tip>`. Review the patch's
files and commit messages before applying it on a public task branch with
`git am <patch-file>`. The maintainer applying it owns conflict resolution:
preserve the public policy and existing API, inspect each conflict, and stop the
backport if its intended behavior is unclear. Never resolve conflicts by
copying the private tree wholesale. Keep unsafe patches outside public history.

Run the affected [library fixtures](../../fixtures/README.md), the example
generation check, and working-file privacy checks before accepting the patch:

```sh
python3 assets/tools/render-help-example.py --check
python3 assets/tools/test-release-privacy.py
python3 assets/tools/check-release-privacy.py --worktree --gitleaks /path/to/gitleaks
```

Working-file mode includes tracked and unignored new files; it is a development
check. A release uses an exact committed revision instead:

```sh
python3 assets/tools/check-release-privacy.py --revision HEAD --gitleaks /path/to/gitleaks
```

The checker requires Gitleaks **8.30.1** and Python 3. It scans committed Git tree
entries directly, including tracked paths matched by ignore rules and paths
marked `export-ignore`. Symlinks are scanned as target text and never followed.
Missing tools/configuration, unreadable data, invalid revisions, or scanner
errors fail the check. Findings report locations and rules without matched
values. Inline scanner allow comments and local scanner ignore files do not
bypass the release scan.

The [privacy policy](../release/privacy-policy.json) identifies six removed
screenshot versions by content digest, so renaming an original image does not
make it acceptable. Image pixels and metadata still require review; passing a
text scanner cannot certify a new screenshot. The safe help illustration is
generated by the real library renderer and retained as text plus SVG.

## Release boundary

These scripts are manually invoked; they add no CI workflow or flake output.
They check the chosen tree, not all earlier history. Releasing history also
requires scanning all objects reachable from the selected refs, reviewing
commit/tag messages and image versions, and restoring the sanitized bundle.
Adding a historical tag expands that verification boundary. Private recovery
copies, original refs, assessment notes, and private audit artifacts remain
outside the public tree and Git object database.

The library lock remains fixed during cleanup. Native fixture builds may fetch
locked dependencies; they must not update the lock. Four-platform evaluation
does not establish runtime coverage on all four platforms. Hoagie's later pin
updates and anonymous public dependency resolution are separate release work.
