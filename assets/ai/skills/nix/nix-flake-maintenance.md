# Nix Flake Maintenance

Use this workflow whenever work changes, diagnoses, or reviews Nix expressions,
flakes, NixOS, Home Manager, packages, overlays, dev shells, flake inputs,
`flake.lock`, or configuration generated by Nix.

## Inspect before acting

1. Read the applicable repository instructions and nearby architecture or
   validation documentation.
2. Inspect the current branch, worktree status, and relevant diff. Preserve all
   existing changes; never assume an unexpected edit is disposable.
3. Locate the producer and consumer of the value being changed. Identify
   whether it is a flake output, module option, module argument, package,
   overlay, passive data value, or generated artifact.
4. Read the smallest complete dependency path needed to understand the change.
   Prefer repository commands and established ownership boundaries.
5. For non-trivial work, record the observable option, output, generated-file,
   or runtime contract and identify generic infrastructure that should remain
   unchanged.

## Change discipline

- Make the smallest change that fully satisfies the request.
- Keep module declarations, passive data, rendering, and activation concerns in
  their established layers.
- Keep evaluated domain data, Nix decision logic, generated presentation, and
  activation or runtime side effects distinct. Convert semantic Nix values to
  strings only at their consumer boundary.
- Preserve public option names, output attributes, defaults, and lock state
  unless changing them is part of the request.
- Do not introduce an overlay, helper library, custom module system, or shared
  abstraction for a single caller without demonstrated complexity reduction.
- Do not manually edit `flake.lock`. Use the repository's supported Nix command
  when an input change requires lock regeneration, and inspect the resulting
  diff for unrelated updates.
- Do not run rebuild, switch, activation, deployment, or publication commands
  unless the user explicitly requests the resulting state change.
- Implement larger changes as vertical slices that can be evaluated and
  inspected independently. Do not accumulate several unverified ownership
  changes before checking the first boundary.

## Source and ownership documentation

- Document non-obvious module arguments, forwarded attributes, normalized
  inputs, and imported attribute contracts beside the boundary where they are
  consumed.
- Trace authoritative values from producer to consumer. Do not infer source
  provenance from filenames, attribute names, or directory conventions when a
  loader or provider can supply it explicitly.
- Keep provenance comments short and factual. Do not annotate obvious standard
  module arguments unless their source is unusual in that file.
- Update an adjacent provenance comment in the same change when its source or
  consumer moves.

## Nix accuracy rules

- Distinguish syntax parsing, evaluation, derivation realization, and
  activation. Passing one does not prove the next.
- Keep `imports` structurally resolvable; do not make module imports depend on
  `config`.
- Use typed module options and preserve Nix merge semantics. Reach for
  `mkDefault`, `mkOverride`, `mkForce`, `mkBefore`, or `mkAfter` only when their
  precedence behavior is intentional.
- Use `nix eval --raw` only for string outputs. Use `--json` for booleans,
  numbers, lists, and attribute sets.
- During read-only diagnosis, prefer `--no-write-lock-file` when evaluation
  could otherwise update the lock file.
- Remember that Git-backed flake sources can omit untracked files. If a new file
  is invisible to evaluation, confirm the source type and repository policy
  before staging it or changing the test approach.
- Keep secrets out of Nix store paths, derivations, logs, command output, and
  generated files that may be world-readable.

## Validate proportionally

Use the repository's documented commands when available. Otherwise:

1. Parse each changed `.nix` file with `nix-instantiate --parse`.
2. Run the configured formatter in check mode, or format only the changed Nix
   files with the formatter selected by the flake. When its executable is
   already resolved, invoke it directly to avoid unrelated flake evaluation,
   fetcher locks, or lock-file access.
3. Evaluate the narrowest affected attribute, configuration, or option.
4. Run `nix flake check` or build the affected output when the change crosses
   flake wiring or derivation boundaries and the cost is appropriate.
5. Parse or smoke-test generated shell and configuration fragments with their
   target runtime when practical. Apply
   [nix-generated-shell.md](nix-generated-shell.md) when the change owns
   generated terminal behavior.
6. Test each affected platform when available; explicitly report untested
   platforms and checks that could not run.

Treat a failed relevant check as evidence to investigate. Do not retry blindly,
silently weaken the check, or report success based on a different validation
boundary.

Before delivery, re-read every changed file and inspect the final diff for
unrelated edits, accidental lock churn, stale names, and incomplete wiring.
Report what changed, what was verified, and any remaining limitation.
